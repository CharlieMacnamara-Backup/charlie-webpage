Marty, a generational talent, runs the shop. He hand-sews kilts from memory,
working alone in a showroom that's barely changed since his Father's Day.

His methods, while proven, showed age: calendar bookings misplaced, missed
calls, staying late to rewrite orders. He was keen on upgrading — the old site
was down for years.

## The Requirements

Expecting a kilt maker to learn new tools after he's been working on paper for
decades is unrealistic. Every tool feels familiar.

I'd already built [Sicamon](https://sicamon.com) — a full
[Stripe](https://stripe.com/) <Definition term="CMS">CMS</Definition> with
digital cataloguing. Understandably, this was too much change. Not looking to
become an overnight online shop.

Best stick to what he's always done.

Project runs on:

- <Definition term="workers">Workers</Definition>
- <Definition term="D1">[D1](https://developers.cloudflare.com/d1/)</Definition>
- <Definition term="KV">[KV](https://developers.cloudflare.com/kv/)</Definition>
- <Definition term="turnstile">Turnstile</Definition>
- <Definition term="resend">Resend</Definition>
- [Next.js](https://nextjs.org/)
- [Tailwind](https://tailwindcss.com/)
- [Google Calendar](https://developers.google.com/calendar/api/guides/overview)
- [GitHub Actions](https://github.com/features/actions)

The stack costs nothing to run — Workers scale between bookings and free tiers
cover traffic. Each worker deploys independently, minimising risk.

### The Workers

**Admin Dashboard Worker** — Order management backed by
[<Definition term="D1">D1</Definition>](https://developers.cloudflare.com/d1/).
Status tracking, CSV exports, automated emails.

**Calendar Worker** — Dedicated worker with its own credentials. Talks to Google
Calendar for slot management — availability checks, event creation, and closure
detection.

**Frontend Worker** — The shop window. Serves every page — hero, map, services,
the tartan search widget, reviews, and the booking button. Static build,
globally distributed.

**Reviews Worker** — Pulls Google Reviews on a schedule into
[KV](https://developers.cloudflare.com/kv/). Fresh content, zero effort.

### The Booking Pipeline

- **Bot detection** — <Definition term="turnstile">Turnstile</Definition>,
  invisible
- **Input validation** — malformed data rejected
- **Closure check** — reads `[Closed]` calendar events
- **Slot availability** — no double-booking
- **Event creation** — writes to Google Calendar
- **Cancel link** — signed <Definition term="JWT">JWT</Definition> in the event
- **Notifications** — <Definition term="async">async</Definition> emails to both
  customer and site owner, never blocks

## The Admin Dashboard

The private notepad replacement page. Independent
[Cloudflare Worker](https://workers.cloudflare.com/) backed by
[D1](https://developers.cloudflare.com/d1/). The same order in the diary, on a
slip, and on a sales pad. Now programmatic.

<SingleImage
  src="/blog/davison-menswear/screenshot-admin-full.png"
  alt="Full admin dashboard view with all management features"
  orientation="horizontal"
  caption="Full admin dashboard"
/>

**Four statuses**: In Progress, Ready, Delivered, Cancelled. Every transition
logged immutably — who changed it, when, and whether the email went out.

**Emails** fire on status changes via [Resend](https://resend.com/). The receipt
includes bank details — stored as Worker secrets, never in the codebase. On
creation, the customer gets payment instructions. When ready, a collection email
fires.

**CSV export**: current tax year, last year, or custom range. Clean totals.

**Quick Add** for reconciling past orders. Archived orders auto-purge after 30
days. No payments on-platform — bank transfer, cash, or the till.

**Add Single Order** is the typical entry point, with an option for group
orders.

## Testing

This runs a business. If a booking drops, that's a customer standing outside a
locked shop.

Five stages sit between production. **Static audits** catch hardcoded
secrets and broken contracts before a test even runs. **Worker tests**
(<Definition term="vitest">Vitest</Definition> + Miniflare) mock every external
dependency.

**Integration and E2E tests** prove real integrations work (Google Calendar,
Resend, Turnstile) and drive the full booking flow and admin lifecycle.

**Pre-deploy checks** probe all workers before deployments. If something's
degraded, the deploy stops. Once live, **post-deploy monitoring** probes every
six hours, runs a worker self-check, and
[<Definition term="lighthouse">Lighthouse</Definition>](https://developer.chrome.com/docs/lighthouse/)
scores every deploy.

### CI/CD

Every push to `main` runs lint, [TypeScript](https://www.typescriptlang.org/),
audit rules, worker tests, and
[<Definition term="playwright">Playwright</Definition>](https://playwright.dev/)
. If they pass, Workers deploy in sequence: calendar first, then reviews, admin
dashboard with D1 migrations, then the main site.

Health probes verify endpoints mid‑pipeline. The site uses a safe rollout: build, upload, promote.
