The shop's been in his family since 1927. Marty is third-generation. He
hand-sews kilts from memory — a generational talent. He works alone in a
showroom that's barely changed since his father's day.

His methods showed their age: calendar bookings misplaced, missed calls, staying
late to rewrite orders. Marty was keen on upgrading — the old site was down for
years — we sat down and talked through what he needed.

## The Requirements

Expecting a sole-trader kilt maker to learn new tools after he's been working on
paper for decades is unrealistic. Every tool looks and feels familiar and
intuitive.

I'd already built [Sicamon](https://sicamon.com) — a full Stripe CMS with
digital cataloguing. Understandably, this was too much change. Not looking to
become an overnight online shop. Stick to what he's always done.

Project runs on:

- <Definition term="workers">Workers</Definition>
- <Definition term="D1">[D1](https://developers.cloudflare.com/d1/)</Definition>

- Turnstile
- <Definition term="resend">Resend</Definition>
- [GitHub Actions](https://github.com/features/actions)

The whole stack costs nothing to run.

### The Booking Pipeline

- **Bot detection** — <Definition term="turnstile">Turnstile</Definition>,
  invisible
- **Input validation** — malformed data rejected
- **Closure check** — reads `[Closed]` calendar events
- **Slot availability** — no double-booking
- **Event creation** — writes to Google Calendar
- **Cancel link** — signed <Definition term="JWT">JWT</Definition> in the event
- **Notifications** — <Definition term="async">async</Definition> emails to both
  customer and site owner, never blocks

[Cloudflare](https://cloudflare.com) secures everything. Someone else books the
slot mid-form? You're told before you finish reading.

Set closures by adding `[Closed]` directly to Google Calendar — Christmas,
holidays, any day off. The worker handles it automatically.

### Testing

This runs a business. Every commit, every deploy — it has to work. If a booking
drops, it's a customer standing outside a locked shop.

<SingleImage
  src="/blog/davison-menswear/testing-pipeline.svg"
  alt="Testing pipeline from static audits through to post-deploy monitoring"
  orientation="horizontal"
  caption="Seven layers between a push and production"
/>

Seven layers sit between a push and production. **Static audits** catch
hardcoded secrets and broken contracts before a test even runs. **Worker tests**
mock every external dependency so internal logic validates deterministically —
no network, no credentials. **Live API tests** then prove the real integrations
work (Google Calendar, Resend, Turnstile). **E2E and integration tests** drive
the full booking flow and admin lifecycle headless.

A **pre-deploy check** probes all four workers before anything ships. If
something's degraded, the deploy stops. Once live, **scheduled monitoring**
probes every six hours, and the calendar worker self-checks every sixty seconds.

### The Workers

**Frontend Worker** — The shop window. Serves every page a visitor lands on —
hero, map, services, the tartan search widget, reviews, and the booking button.
Static build, globally distributed. No server to babysit.

**Calendar Worker** — Looks after the booking system — a separate worker with
its own credentials. [Google Calendar](https://calendar.google.com/) is the
database, zero new infra, already in use. Reads `[Closed]` events, checks slot
availability, writes new bookings, and generates cancel links using signed

<Definition term="JWT">JWTs</Definition> in the event description — no database
lookup needed. [Turnstile](https://www.cloudflare.com/products/turnstile/) over
CAPTCHA on the booking form: free, invisible, no learning curve. Email fires
asynchronously, so the booking never blocks on a delivery failure.

**Reviews Worker** — Pulls Google Reviews on a schedule into
[KV](https://developers.cloudflare.com/kv/). Stays current without input — fresh
content, zero effort.

## The Admin Dashboard

The notepad replacement — its own
[Cloudflare Worker](https://workers.cloudflare.com/) backed by
[D1](https://developers.cloudflare.com/d1/). The same order in the diary, on a
slip, and on a sales pad — three times, one customer. Now it's a page.

<SingleImage
  src="/blog/davison-menswear/screenshot-admin-full.png"
  alt="Full admin dashboard view with all management features"
  orientation="horizontal"
  caption="Full admin dashboard — 139 tests verify the whole system"
/>

Four statuses: In Progress, Ready, Delivered, Cancelled. Every transition logged
immutably — who changed it, when, and whether the email went out. Group orders
for wedding parties — groom, best man, ushers under one accordion. Measurements:
kilt waist, seat, length, jacket chest, sleeve, back, height, and build notes.
All optional. CSV export: current tax year, last year, or custom range. Clean
totals at the bottom for the accountant.

Emails fire on status changes via [Resend](https://resend.com/). The receipt
includes bank details — stored as Worker secrets, never in the codebase. On
creation, the customer gets payment instructions — no Stripe, that was a
deliberate choice. When it's ready, a collection notice. Not a word typed.

Quick Add for reconciling past orders. Archived orders auto-purge after 30 days.
No payments on-platform — bank transfer, cash, or the till. Progress without
overwhelm.

Add Single Order is the entry point. Resend emails bank transfer details on
creation and a collection notice when ready.
